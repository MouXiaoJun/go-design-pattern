# 状态模式 State Design Pattern

**分类：** 行为型模式，把对象在不同状态下的行为封装进独立的状态对象，状态转移也由状态对象自己完成。

**定义：**

状态模式解决的是「状态驱动的行为」问题：一个对象在不同状态下对同一个动作的反应不同，比如订单在「待支付」和「已发货」时，调用「发货」一个该报错一个该成功。如果不用状态模式，就得在动作方法里写一堆 `if/switch` 分支判断当前状态，状态越多越难维护。状态模式把每个状态封装成一个对象，状态对象既定义该状态下各动作的行为，又负责「动作完成后转移到哪个状态」，把条件分支拆成一个个独立的类。

在 Go 中落地用接口 + 组合：定义一个 `State` 接口，每个状态是一个实现了该接口的结构体；上下文对象（`Order`）持有一个 `State` 接口字段，动作方法直接委托给当前状态对象处理，状态对象执行动作后修改上下文的 `state` 字段完成转移。Go 没有继承，状态之间靠实现同一接口建立多态关系。

**实现方法：**

1. 定义状态接口，声明所有动作方法（如 `Pay`、`Ship`、`Complete`）。
2. 为每个状态实现该接口：合法的动作修改上下文状态完成转移，非法的动作返回错误。
3. 上下文对象持有 `state State` 字段，动作方法直接 `return o.state.xxx(o)` 委托出去。
4. 初始化时把上下文设置为初始状态。

**是否使用：**

- 适用场景：对象行为随状态变化，且状态数量较多、转移规则较复杂，如订单状态机、审批流、TCP 连接状态、游戏角色状态。
- 判断标准：当你发现代码里出现了大量基于状态的 `if/switch` 分支，且每次加状态都要改这些分支时，就该考虑状态模式。
- 需要警惕：状态很少、转移很简单时，用状态模式是过度设计，几个 `if` 反而更直观。
- 现实项目里的状态机框架（如 workflow、状态机库）本质就是这个模式：把状态、转移、动作、守卫条件都结构化地配置出来，状态模式是它们的代码级原型。

**Go 落地要点：**

- 用接口抽象状态，上下文依赖接口而非具体状态，便于扩展新状态。
- 状态对象是无状态的结构体，可以定义成全局单例复用，避免每次转移都 new 一个新对象。
- 转移逻辑放在状态对象内部，上下文只负责「委托」，不关心业务规则。
- 非法的状态转移用返回 error 表达，而不是 panic，让调用方可以优雅处理。
- 若状态对象需要在转移时携带数据或执行副作用，把上下文指针传给状态方法即可。

**相关模式：**

- 策略模式：两者结构几乎一样，都是接口 + 组合 + 委托；区别在于策略是「可替换的算法」，状态是「对象自身会变化的行为」，状态之间知道彼此的转移关系。
- 有限状态机：状态模式是 FSM 的面向对象实现，复杂状态机可借助状态机框架进一步结构化。
