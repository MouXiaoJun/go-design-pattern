# 中介者模式 Mediator Design Pattern

**分类：** 行为型模式，用一个中枢对象统一协调多个对象之间的交互，让对象之间不再直接互相引用。

**定义：**

中介者模式解决的是「网状交互」问题：当多个对象两两之间都要通信时，对象之间会形成 N×(N-1) 条互相引用的连线，耦合度极高，改一个对象会牵动一片。中介者模式把这些交互收拢到一个中枢对象里，各对象只依赖中介者，消息的转发、路由、过滤都由中介者统一处理，对象之间从网状关系退化成星形关系。

在 Go 中落地，通常用接口定义中介者的职责，用具体的结构体实现这个接口；各个「同事」对象只持有中介者的接口引用，通过中介者把消息转发给其他同事。Go 没有继承，同事之间通过组合中介者接口来建立联系，转发逻辑集中在中介者的方法里。

**实现方法：**

1. 定义中介者接口（如 `Mediator`），声明协调方法：注册、点对点转发、广播等。
2. 实现具体中介者（如 `ChatRoom`），内部维护一张同事对象的表，实现转发与路由逻辑。
3. 定义同事对象（如 `User`），它只持有中介者接口，不持有其他同事的引用。
4. 同事对象发起交互时调用中介者，由中介者把消息送到目标同事。

**是否使用：**

- 适用场景：一组对象之间存在复杂的网状交互，且交互逻辑经常变化，例如聊天室、交通管制塔、GUI 组件的联动。
- 判断标准：当你发现对象 A、B、C 互相持有对方的引用、转发逻辑散落各处难以维护时，就该考虑引入中介者。
- 反之，如果对象之间交互简单、连线很少，引入中介者反而多了一层间接，得不偿失。
- 需要警惕：中介者容易变成「上帝对象」，把太多逻辑都塞进中枢里，让它自己膨胀成一个难以维护的大类。

**Go 落地要点：**

- 用接口表达中介者职责，同事依赖接口而非具体实现，方便替换（例如测试时注入 mock 中介者）。
- 中介者内部用 map 维护同事对象，按名字或 id 路由。
- 转发逻辑集中在中介者的方法里，同事对象只负责「发送」和「接收」，不关心路由细节。
- 如果中介者状态需要并发访问，注意加锁（如 `sync.RWMutex`），聊天室这类场景通常会有并发写入。

**相关模式：**

- 观察者模式：中介者可以做「多对多」协调，观察者偏向「一对多」的广播通知；两者常被混用。
- 门面模式：门面是给外部一个简化入口，中介者是协调内部对象之间的交互，方向相反。
