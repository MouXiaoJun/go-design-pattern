# 建造者模式 Builder Design Pattern

**分类：**创建型。把一个复杂对象的构建过程拆成独立步骤，通过设置不同可选参数定制化创建。

**定义：**当一个对象的构造参数很多、且参数之间有依赖或约束关系时，把「参数校验 + 分步构建」从构造函数里拆出来，放到 Builder 里，构建过程对调用者透明。

## 为什么需要建造者模式

- **构造函数和 set 方法的局限性**
  - 构造函数参数过多导致可读性差
  - set 方法无法校验必填项
  - 属性之间的依赖关系或约束条件无法校验
  - 创建不可变对象的需求
- **建造者模式的解决方案**
  - 将校验逻辑放置到 Builder 类中
  - 创建不可变对象

## 和工厂模式的区别

- **工厂模式**：用于创建不同但相关类型的对象；由给定的参数决定创建哪种类型的对象
- **建造者模式**：用于创建一种类型的复杂对象；通过设置不同的可选参数来定制化创建不同的对象

## 实现方法

1. 定义产品结构体，字段**不可变**（Go 里用小写 + 只读方法暴露）
2. 定义一个 Builder（或一组可选参数），每个参数有默认值
3. 设置参数后统一做**必填与约束校验**
4. 校验通过才构建最终对象，失败返回 error

## 是否使用

- **何时用**：构造参数 ≥ 4 个、存在必填项、参数之间有依赖约束、需要不可变对象
- **慎用**：参数只有两三个、没有校验需求时，直接构造函数或普通 struct 字面量更简单
- Go 里多数「建造者」场景被**函数式选项（functional options）**替代，见下

## Go 落地要点

- **函数式选项是最 Go 的建造者**：`NewXxx(name string, opts ...Option)`，每个选项是 `func(*config)`，可带默认值、逐个覆盖、构造时统一校验（见 `option.go`）
- 相比经典 Builder 类，函数式选项：调用更简洁、不需要中间对象、天然支持默认值
- 真正的 Builder 类写法（`builder.go`）在 Go 里只在「构建过程本身很复杂、需要分阶段」时才有必要

## 相关模式

- **工厂模式**：关注创建哪种类型；建造者关注怎么把一个复杂对象拼出来
- **原型模式**：复制已有对象，另一种避免复杂构造的方式
