# 外观模式 Facade Design Pattern

**分类：** 提供一个统一的高层接口，把一组复杂子系统的交互简化成一个入口。

**定义：**

- 解决什么问题
  - 客户端要完成一件事需要按顺序调用多个子系统，调用方被迫了解每个子系统的细节和调用顺序。
  - 子系统之间耦合复杂，客户端代码重复且脆弱，任一子系统变化都会牵连大量调用方。
- Go 中怎么落地
  - 定义门面结构体，组合持有多个子系统对象（组合）。
  - 对外只暴露少数方法，内部编排子系统的调用顺序与异常处理。
  - 子系统的方法保持小写（包内可见），从语法上强制调用方只能走门面。

**实现方法：**

- 识别子系统：库存、支付、通知等各自独立的服务。
- 定义门面：一个 `OrderService`，对外只暴露 `PlaceOrder`。
- 编排流程：门面内部依次调用 `check → charge → deduct → send`，并统一返回 error。

**是否使用：**

- 使用场景
  - 一个功能横跨多个子服务，调用方只看得到一堆内部细节。
  - 需要给外部（如对外 API、SDK）提供简单稳定的入口，隔离内部复杂实现。
- 判断标准
  - 门面不新增业务能力，只做“编排与简化”；如果门面里塞满了真正的业务逻辑，说明职责跑偏了。

**Go 落地要点：**

- 门面保持薄：只做转发与顺序编排，不承载业务规则。
- 对外接口尽量少而稳定，子系统改动只影响门面内部。
- 门面内部的子系统对象在构造函数里组装，便于依赖注入与测试替换。
- Go 生态里 `http.Server`、`sql.DB` 这类对象本身就是门面，屏蔽了内部大量复杂细节。

**相关模式：**

- 适配器模式：适配器转换接口形态，门面简化接口数量。
- 中介者模式：门面是静态的简化入口，中介者负责对象间动态的通信协调。
