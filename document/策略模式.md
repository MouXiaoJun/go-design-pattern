# 策略模式 Strategy Design Pattern

**分类：**行为型模式。定义一族可互相替换的算法，把它们封装成独立对象，让算法的选择与使用分离开，客户端可以在运行时挑选或切换算法。

## 定义

- 解决的问题：一个行为（比如支付、排序、折扣计算）有多种实现方式。如果直接写 if/else 分支，每新增一种算法都要改原有代码，调用方也被迫了解所有分支细节。
- 核心做法：把每一种算法封装成一个实现同一接口的对象（策略），再通过一个上下文对象持有当前策略；调用时只面向接口，不关心具体是哪个实现。
- Go 中的落地：
  - 接口方式：定义 `Payment` 这样的策略接口，支付宝、微信、银行卡分别实现；上下文 `Order` 持有 `Payment`，客户端通过构造函数或 setter 注入具体策略。
  - 函数方式：Go 的一等函数可以直接当策略，`type SortStrategy func([]int)` 一个函数类型就能表达「一组算法」，调用方传函数即可，连接口和 struct 都省了。

## 实现方法

1. 定义策略接口，方法签名即算法族的共同契约。
2. 为每种算法写一个实现类型。
3. 写一个上下文类型，持有策略接口字段，暴露一个执行方法把调用转发给策略。
4. 客户端在创建上下文或运行时，注入、切换具体策略。

## 是否使用

- 适合：
  - 同一行为有多种实现，且会经常新增、替换算法。
  - 需要根据配置、运行环境或用户选择动态切换算法。
  - 想把一堆 if/else 拆开，避免每次加分支都改核心逻辑。
- 不适合：
  - 只有一两种固定写法且几乎不变，直接 if/else 更省事。
  - 算法之间差异很大、没有稳定的共同契约，强行抽接口只会更绕。

## Go 落地要点

- 接口 + 注入 和 函数类型 + 参数传入 两种写法的取舍：
  - 接口方式：策略带状态、方法不止一个、或需要多个相关方法一起替换时，用接口更合适；可读性更强，但每种算法要一个 struct。
  - 函数方式：策略只有一个无状态操作（一个函数能表达）时，用函数类型更简洁，`sort.Slice`、`http.HandlerFunc` 都是这种思路；代价是策略不能再挂额外状态。
- 上下文只管「持有 + 调用」策略，不要自己去判断该用哪个；选择策略的职责留给客户端（或工厂）。
- 策略尽量无状态、可复用；切换策略用 setter 或构造参数注入，而不是硬编码。

## 相关模式

- 与状态模式：结构相似（都持有接口并转发），但状态模式关注对象内部状态迁移，策略模式关注算法可替换。
- 与工厂模式：工厂负责「造出」合适的策略，策略模式负责「使用」策略，常搭配使用。
