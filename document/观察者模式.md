# 观察者模式 Observer Design Pattern

**分类：** 行为型模式，主题状态变化时自动通知所有订阅者，形成一对多的广播。

**定义：**

观察者模式解决的是「状态变化联动」问题：一个对象（主题）的状态变了，一群对象（观察者）都需要感知并做出反应，比如股价变了要推送给所有订阅者、用户上线要通知所有关注者。观察者模式把「谁在关心我」这件事从主题里抽出来，主题只维护一份订阅者列表，状态变化时统一广播，订阅者可以随时加入或退出，主题和订阅者之间松耦合。

在 Go 中，最贴合语言习惯的落地是用 channel：主题维护 `map[id]chan T`，订阅者拿到只读通道消费事件，主题状态变化时向各通道发送。这种写法天然适合并发，订阅者自己起 goroutine 消费，避免了回调函数满天飞。

**实现方法：**

1. 主题维护订阅者集合，例如 `map[string]chan T`。
2. `Subscribe` 创建通道、登记订阅者，返回只读通道给订阅者。
3. 状态变化时遍历订阅者通道广播事件。
4. `Unsubscribe` 把订阅者从集合移除（并关闭通道），防止泄漏。

**是否使用：**

- 适用场景：一对多的状态通知，如消息推送、事件总线、配置变更通知、行情推送。
- 判断标准：当「一个状态变化要触发多个对象更新」，且这些对象数量、类型会动态变化时，用观察者模式。
- 需要警惕：广播阻塞与 goroutine 泄漏——如果订阅者消费慢，广播方会被拖住；如果订阅者不取消订阅，通道和 goroutine 会一直留着。

**Go 落地要点：**

- 用 channel 而非回调接口，是 Go 里更自然的观察者实现，订阅者用 goroutine `for range ch` 消费。
- 避免阻塞：通道加缓冲（如 `make(chan T, 1)`），发送用 `select + default` 非阻塞发送，订阅者消费不及时就丢弃本次更新，广播方永远不会被卡住。
- 避免泄漏：取消订阅时必须 `close` 通道并 `delete` 出集合；用 `sync.RWMutex` 保护订阅者集合，因为订阅/退订/广播可能并发发生。
- 权衡：非阻塞 + 小缓冲意味着订阅者可能错过中间状态，只适合「最新值即可」的场景（如行情快照）；需要每条都不丢时，要改用足够大的缓冲或背压策略。

**相关模式：**

- 中介者模式：中介者协调「多对多」，观察者做「一对多」广播，事件总线常是两者的结合体。
- 发布订阅模式：观察者的泛化版，发布者和订阅者之间通过消息队列/事件通道彻底解耦，甚至跨进程。
