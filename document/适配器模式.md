# 适配器模式 Adapter Design Pattern

**分类：** 结构型模式——把一个已有的不兼容接口包装成客户端期望的接口，让原本无法协作的两个对象能无感配合。

## 定义

解决的问题：老系统或第三方库提供的接口和新代码期望的接口不一致（方法名、参数、返回类型对不上）。直接改老代码风险大，直接迁就老接口又会让调用方耦合。

Go 中的落地：新代码面向接口编程，写一个适配器"包裹"被适配对象，把新接口的方法翻译成对老接口的调用。Go 里有两条惯用手法：

- 对象适配器：适配器持有一个老对象，实现新接口，方法内部转发调用
- 函数适配器：定义一个函数类型并为其实现接口方法（类比 `http.HandlerFunc`），把一个普通函数"改造成"接口实现

## 实现方法

1. 明确目标接口：新系统期望的接口 `PaymentService`
2. 找到待适配的老接口：老网关的 `Charge(amount, cardNo)`
3. 写适配器 `GatewayAdapter`，内部持有老对象，实现 `Pay` 方法并做参数映射
4. 客户端面向 `PaymentService` 编程，注入适配器实例

## 是否使用

- 想复用已有的、接口不匹配的类或库，又不想修改它的源码
- 新老系统并行过渡期，需要把老实现包一层接入新架构
- 需要把多个来源不同、接口各异的实现统一到一个共同接口

判断标准：如果接口一开始就能由你设计且双方可控，优先直接把接口设计一致，别先写出两个不兼容接口再靠适配器打补丁。

## Go 落地要点

- 适配器不引入新业务逻辑，只做"接口翻译 + 参数映射"
- `http.HandlerFunc` 是函数适配器的标准范例：一个函数类型通过一个方法即可实现 `http.Handler`
- Go 的隐式接口让适配器无需显式声明"实现某接口"，写完方法即满足接口
- 结构体嵌入可复用部分行为，但适配器通常需要重新映射方法，嵌入更适合"复用实现"而非"翻译接口"

## 相关模式

- 外观模式：适配器让"一个接口"适配"另一个接口"，外观则是给"一组接口"提供统一入口
- 装饰器模式：装饰器保持接口不变并增强行为，适配器则改变接口
