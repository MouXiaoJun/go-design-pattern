# 模板方法模式 Template Method Design Pattern

**分类：**行为型模式。在父类中固定算法的骨架（步骤顺序），把某些步骤延迟到子类实现，从而在不改变整体流程的前提下，让子类改写个别步骤。

## 定义

- 解决的问题：一类任务整体流程固定，只有其中一两个步骤因场景而异。把流程重复写在每个实现里，既重复又容易改漏。
- 核心做法：把不变骨架抽到一个模板里，把可变步骤抽象成接口/钩子，模板方法按固定顺序调用这些步骤。
- Go 中的落地：Go 没有继承和虚函数，无法像 Java 那样直接让子类覆写父类方法。常见的模拟方式是「结构嵌入 + 接口注入」：
  - 模板 struct 持有一个步骤接口（可变步骤）。
  - 具体 struct 嵌入模板 struct 以复用骨架方法，同时实现步骤接口，并在构造时把自己注入为模板的步骤实现。
  - 骨架方法运行到可变步骤时，通过接口回调到具体 struct 的实现，等价于「子类覆写」。

## 实现方法

1. 定义可变步骤的接口（如 `Processor`）。
2. 写模板 struct，持有该接口字段，并实现骨架方法（读 → 处理 → 写），中间的可变步骤调用接口。
3. 写具体 struct，嵌入模板 struct，实现步骤接口。
4. 构造具体 struct 时，把自身注入为模板的步骤实现。
5. 客户端调用嵌入的骨架方法即可。

## 是否使用

- 适合：
  - 多个流程骨架一致、只有个别步骤不同（如数据处理管道、冲泡类流程、请求处理中间件链）。
  - 想把「顺序」和「具体步骤」解耦，新增场景只改步骤不改骨架。
- 不适合：
  - 流程本身差异很大、没有稳定骨架时，强行抽模板反而别扭。
  - 可变点非常多、步骤又互相纠缠时，模板会退化成一张难维护的钩子清单。

## Go 落地要点

- 没有继承，用「嵌入复用骨架 + 接口回调可变步骤」模拟覆写，构造函数里 `p.processor = p` 这一步是关键，漏了会导致空接口调用。
- 可变步骤尽量保持单一、无副作用，便于组合和测试。
- 如果骨架只是一小段顺序逻辑，也可以直接用「函数参数 + 闭包」表达，不必非得上 struct 嵌入；模板方法更适合流程较长、步骤较多的情况。

## 相关模式

- 与策略模式：模板方法用继承/嵌入固定「流程」，可变的是「步骤」；策略模式用组合替换「整个算法」。两者常互相转化。
- 与工厂方法：模板方法的某个步骤可以用工厂方法创建对象。
