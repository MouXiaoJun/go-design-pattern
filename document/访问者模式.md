# 访问者模式 Visitor Design Pattern

**分类：**行为型模式。在不修改元素类的前提下，把作用于一组对象结构上的新操作集中到一个访问者对象里，实现对元素的双分派。

## 定义

- 解决的问题：对象结构里有一组不同类型（如 AST 节点、几何图形），要给它们反复添加新操作（求值、格式化、检查、求面积、求周长）。如果把每个操作都写进元素类，每加一个操作就得改所有元素类。
- 核心做法：把操作从元素中抽出来，集中到访问者里；元素提供一个 `Accept(visitor)` 方法，把「自己是谁」通过具体类型的回调传给访问者，从而在一次调用里同时确定「元素类型」和「操作」——即双分派。
- Go 中的落地：
  - 元素接口 `Shape` 只负责 `Accept(Visitor)`。
  - 访问者接口 `Visitor` 为每种具体元素声明一个方法（`VisitCircle`、`VisitRectangle`）。
  - 每种操作是一个访问者实现（面积、周长），加操作只需新增访问者，元素类不动。

## 实现方法

1. 定义元素接口，声明 `Accept(visitor)`。
2. 定义访问者接口，为每种元素类型声明一个 visit 方法。
3. 每个具体元素实现 `Accept`，方法体就是 `visitor.VisitXxx(this)`，完成第一次分派。
4. 每个具体访问者实现所有 visit 方法，完成第二次分派。
5. 使用方把元素集合传给访问者，逐一遍历调用。

## 是否使用

- 适合（类型分派频繁且会扩操作）：
  - 对象结构类型较稳定，但要对它持续添加新操作（如 AST 上的求值、类型检查、格式化）。
  - 操作依赖元素内部数据、又希望把同类操作集中在一个文件里，而不是散落在各元素类。
- 不适合（类型集小且稳定时，直接 type switch 更简单）：
  - 元素种类很少、又不常加新操作，用 `switch v := s.(type)` 一次写清反而更直接。
  - 元素类型频繁新增，访问者接口每加一种元素就要改所有访问者，代价会反过来压过收益。

## Go 落地要点

- 双分派的实现关键是 `Accept` 里把具体类型 `*Circle` 传给 `VisitCircle`，Go 通过接口 + 按类型命名的方法完成分派。
- 访问者接口按元素类型拆方法，新增元素类型会破坏所有已有访问者，这是它的主要成本；反之新增操作零成本。
- Go 没有方法重载，visit 方法要手动命名成 `VisitCircle`/`VisitRectangle` 之类，不能像 Java 那样都叫 `visit`。
- 小场景优先 type switch：类型集小且稳定时，`switch s.(type)` 代码更少、更好读，不必为「未来可能加操作」提前上访问者。

## 相关模式

- 与迭代器：访问者常配合遍历对象结构，迭代器负责「怎么走」，访问者负责「走到后做什么」。
- 与组合模式：组合出的树形结构是访问者的典型用武之地。
