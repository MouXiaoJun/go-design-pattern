# 命令模式 Command Design Pattern

**分类：** 行为型模式——把一次请求封装成独立对象，从而支持排队、记录、撤销和重做。

## 定义

**解决的问题：** 直接调用 `editor.insert(...)`、`editor.delete(...)` 时，「执行这个动作」和「动作本身」耦合在一起。一旦需要撤销、重做、批量执行、异步排队，就得在调用处到处写反操作和记录逻辑，越写越乱。

**模式的做法：** 把「一次操作」抽象成 `Command` 对象，它知道两件事——怎么执行（`Execute`）、怎么回滚（`Undo`）。调用方不再直接操作接收者，而是创建命令对象交给一个调用者（Invoker）去执行。命令因此可以被记录成历史栈，撤销就是反向执行栈顶命令。

**Go 中怎么落地：** 接口 + 结构体（或闭包）。接口 `Command` 只有 `Execute()/Undo()` 两个方法；接收者（编辑器）提供最小粒度的原语（插入/删除），命令对象负责「按参数调用原语 + 记住撤销所需的信息」。

## 实现方法

1. 定义接收者（如 Editor），暴露不可再分的基本操作。
2. 定义 `Command` 接口：`Execute()` 和 `Undo()`。
3. 为每种操作实现命令结构体（InsertCommand、DeleteCommand），持有接收者和参数；撤销所需的信息在执行时保存下来。
4. 定义一个 Invoker（如 History），持有 `done`/`undone` 两个栈，提供 Do/Undo/Redo。

## 是否使用

**适用场景：**

- 需要撤销/重做（文本编辑器、绘图、表单）。
- 需要把操作排队、延迟执行或做日志回放。
- 需要解耦「发起操作的对象」和「执行操作的对象」。

**判断标准：** 只要出现「撤销/重做」或「操作要脱离调用时机去执行」，命令模式就是直接答案；如果只是一次性顺序调用，普通函数调用就够，别为了模式而模式。

## Go 落地要点

- 撤销所需的状态（比如被删除的文本）要在 `Execute` 时顺手记下来，`Undo` 才能还原；这是命令模式最容易遗漏的地方。
- `done`/`undone` 两个栈让撤销和重做对称：`Do` 清空 `undone`，`Undo` 和 `Redo` 互相搬运。
- 接收者的基本操作做小、做纯（不做业务逻辑之外的副作用），命令层才容易组合与回滚。

## 相关模式

- 备忘录模式：命令模式常用栈记录历史，备忘录模式则保存对象快照，两者常配合实现深层次撤销。
- 组合模式：命令可以组合成「宏命令」，一次性执行一串命令。
