# 职责链模式 Chain of Responsibility Design Pattern

**分类：** 行为型模式——把请求交给一条由多个处理器串成的链，每个处理器要么处理它，要么把它转交给下一个。

## 定义

**解决的问题：** 一段请求的处理逻辑会随业务不断叠加（鉴权、限流、日志、缓存……），如果把这些判断都堆在一个大函数里，就会变成层层 `if else`，增删某个环节都得改动核心逻辑。

**模式的做法：** 把每个环节拆成独立的处理器，用「下一个处理器」的引用把它们串成一条链。请求从链头进入，每个处理器只关心两件事——这件事归不归我管，不归就调用 `next` 交给后面。任何节点都能提前终止（比如鉴权失败直接返回），也能在调用 `next` 前后各做一段逻辑（before/after）。

**Go 中怎么落地：** 最自然的就是 http 中间件。`net/http` 的 `HandlerFunc` 本身就是「函数即节点」，我们再定义一个带 `next` 参数的处理器接口，用接口 + 闭包把多个中间件包成一个最终的 `http.HandlerFunc`。

## 实现方法

1. 定义处理器接口 `Handler`，方法签名里带一个 `next http.HandlerFunc`，表示「我处理完剩下的交给谁」。
2. 每个具体中间件实现该接口：决定是否调用 `next`，以及是否在 `next` 前后加逻辑。
3. 定义一个 `Chain`，持有中间件列表和最终处理器。
4. 从后往前构建：让每个中间件的 `next` 指向「它后面所有节点串起来的结果」，这一步由闭包完成。

## 是否使用

**适用场景：**

- 请求需要按固定顺序经过多个可插拔的处理步骤（中间件、过滤器、审批流）。
- 处理步骤的顺序或组合在运行时才确定，或需要频繁增删某个环节。

**判断标准：** 当你在一个函数里看到「一长串 `if` 判断、每个分支里还可能 `return`」，而且这些判断彼此独立、顺序可变时，就值得拆成责任链；如果只有一两个固定步骤，直接顺序调用反而更直白。

## Go 落地要点

- `net/http` 中间件就是现成的责任链，写 Web 服务时几乎不用自己造轮子。
- 用闭包串联比「持有 next 指针的结构体」更简洁，但要小心闭包捕获循环变量的坑——在循环里用局部变量快照，而不是直接捕获循环变量。
- 链条短路（某个节点不调 `next`）既是能力也是风险：忘调 `next` 会让请求「断在中间」，要格外小心。
- 错误处理要提前约定：是返回 `error` 让上层统一处理，还是每个节点自己处理并终止。

## 相关模式

- 组合模式：链条本身也可以看成一条「复合处理器」。
- 命令模式：责任链常用来确定「由谁处理」，命令模式则封装「处理什么」。
