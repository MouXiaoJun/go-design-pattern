# 装饰器模式 Decorator Design Pattern

**分类：** 在不改变原类型的前提下，动态地给对象叠加新的职责。

**定义：**

- 解决什么问题
  - 需要给已有类型增加功能，但直接改原类型会违反开闭原则，或者原类型来自第三方库、标准库，无法修改。
  - 需要按任意顺序、任意组合叠加多个功能，且运行时可增删，避免为每种组合各写一个子类。
- Go 中怎么落地
  - 定义一个与目标类型一致的接口，装饰器和被装饰对象都实现它（接口）。
  - 装饰器持有被装饰对象（组合），在转发调用的前后插入新逻辑。
  - 函数式变体：`type Middleware func(http.Handler) http.Handler`，用闭包包装，逐个叠加。

**实现方法：**

- 抽取目标接口：`http.Handler` 本身就是只含 `ServeHTTP` 的接口，无需自建。
- 写装饰器：接收一个 Handler，返回一个新 Handler，内部先做额外逻辑，再调用内层 Handler。
- 叠加：用 `Chain` 按顺序包装，得到最外层 Handler 交给 `http.Server`。

**是否使用：**

- 使用场景
  - 需要在不改原代码的前提下扩展功能：日志、鉴权、限流、加解密、埋点等横切关注点。
  - 功能需要按需组合，且组合顺序敏感（例如先鉴权再限流）。
- 判断标准
  - 装饰器与被装饰对象实现同一接口，客户端无感知；如果只是给单个对象加一个方法，用普通组合即可，不必套装饰器。

**Go 落地要点：**

- 无状态装饰器优先用函数 + 闭包实现，代码最短。
- 有状态装饰器（如限流计数）用结构体持有状态，方法返回装饰后的 Handler。
- 装饰器层层嵌套，注意错误处理与短路逻辑：鉴权失败直接 return，不再调用内层。
- 标准库 `net/http` 的中间件是装饰器模式最典型的落地，`io.Reader`/`io.Writer` 的包装同理。

**相关模式：**

- 代理模式：都通过组合转发，但装饰器强调叠加职责，代理强调控制访问、延迟创建。
- 责任链模式：装饰器侧重“包装同一对象”，责任链侧重“请求在多个处理器间传递”。
