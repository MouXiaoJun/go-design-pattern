# 代理模式 Proxy Design Pattern

**分类：** 提供一个替身来控制对真实对象的访问，可在访问前后附加控制逻辑。

**定义：**

- 解决什么问题
  - 真实对象的创建或调用成本高（大对象加载、远程调用），希望延迟或复用。
  - 需要在访问真实对象前后加控制：权限校验、缓存、限流、审计等，而调用方无感知。
- Go 中怎么落地
  - 定义接口，真实对象与代理都实现它（接口 + 组合）。
  - 代理持有真实对象的引用，转发请求，并在前后插入逻辑。
  - 懒加载用 `sync.Once` 保证只初始化一次；缓存代理用 map + 读写锁。

**实现方法：**

- 定义接口：`UserRepository`。
- 实现真实对象：`DBUserRepository`，模拟慢查询。
- 实现代理：`CachedUserRepository` 先查缓存，未命中才回源并写缓存。
- 懒加载变体：`LazyImage` 用 `sync.Once` 延迟到首次调用才加载。

**是否使用：**

- 使用场景
  - 懒加载：大对象、重资源首次访问时才初始化。
  - 访问控制：无权限的调用者被代理拦截。
  - 缓存：热点数据由代理缓存，减少回源。
  - 远程代理：本地对象代理远程服务（RPC stub）。
- 判断标准
  - 代理与真实对象接口一致、调用方不感知；如果代理改变了接口或语义，应改用适配器或门面。

**Go 落地要点：**

- 代理和真实对象共用一个接口，这是“替身”能被透明替换的前提。
- 懒加载用 `sync.Once`，避免并发下重复初始化。
- 缓存代理用 `sync.RWMutex`：读多写少，读锁允许并发命中缓存。
- 转发时保留真实对象的返回值和 error，代理不要吞掉错误。
- 注意缓存一致性问题：真实数据变更后缓存可能过期，需要失效策略。

**相关模式：**

- 装饰器模式：结构相似，但代理关注访问控制/生命周期，装饰器关注叠加职责。
- 适配器模式：适配器解决接口不匹配，代理保持接口一致。
