# 迭代器模式 Iterator Design Pattern

**分类：** 行为型模式——按顺序访问聚合对象里的每个元素，而不暴露它的内部表示。

## 定义

**解决的问题：** 不同集合的内部结构不同（数组、链表、树、哈希表、惰性流），如果让调用方自己访问内部字段，就会和具体数据结构绑死，换个结构就要改所有遍历代码。

**模式的做法：** 把「怎么遍历」封装成一个迭代器，只对外暴露 `Next()/Value()` 这类最小接口。调用方只依赖迭代器，不关心底层是数组还是树。

**Go 中怎么落地：** 这个模式在 Go 里大部分时候被语言特性「代替」了——`range` 原生支持切片、map、channel、字符串；channel 加 goroutine 又能实现惰性生成。真正需要自己写迭代器的情况很少：主要是树/图的遍历、自定义惰性流，或需要多套遍历顺序的时候。落地时用「`Next() bool` + `Value()`」两步接口，或 channel 的 `for range`。

## 实现方法

1. 定义 `Iterator` 接口：`Next() bool` + `Value()`。
2. 实现具体迭代器，内部持有底层数据和一个游标。
3. 聚合对象提供 `Iterator()` 工厂方法，返回新的迭代器。
4. （可选）用 channel + goroutine 提供惰性遍历，消费方用 `for x := range it` 读取。

## 是否使用

**适用场景：**

- 底层结构不是切片/map，`range` 直接到不了（树、图、文件流）。
- 需要多种遍历顺序（前序/后序/层序），或惰性、可暂停的遍历。

**判断标准：** 如果集合就是切片或 map，直接用 `range`，写迭代器属于过度设计；只有当 `range` 覆盖不了你的结构时，这个模式才值得出现。

## Go 落地要点

- 优先 `range`，它覆盖了绝大多数日常遍历。
- channel 迭代简洁，但要注意：消费方提前 `break` 会阻塞生产者 goroutine（需配合缓冲或 context 取消），而且 goroutine 有额外开销——小集合别用。
- `Next() bool` + `Value()` 的两步接口是 Go 社区的常见写法（`sql.Rows`、`bufio.Scanner` 都是这个风格）。
- 迭代器要能「回到起点」：每次 `Iterator()` 返回新实例，而不是共享一个有状态的单例。

## 相关模式

- 组合模式：树结构常配合迭代器做统一遍历。
- 访问者模式：遍历 + 对每个节点做操作，可以合二为一。
