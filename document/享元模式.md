# 享元模式 Flyweight Design Pattern

**分类：** 通过共享不可变对象，减少大量细粒度对象的重复创建，节省内存。

**定义：**

- 解决什么问题
  - 系统中存在大量相似对象（字符、棋子、地图地块），每个都独立创建会耗尽内存。
  - 这些对象之间只有少部分状态不同，大部分状态可以共享。
- 内在状态与外在状态
  - 内在状态（intrinsic）：对象之间相同、可共享的部分，如字符的字形、字体、颜色。
  - 外在状态（extrinsic）：随使用场景变化的部分，如字符在屏幕上的 x,y 坐标，由调用方在方法参数里传入。
- Go 中怎么落地
  - 享元对象本身不可变，只存内在状态。
  - 工厂（带 `sync.Mutex` 的 map）按内在状态缓存实例，相同 key 返回同一个对象。
  - 调用方把外在状态作为参数传给方法，而不是塞进对象。

**实现方法：**

- 定义享元：`Glyph` 只存字符、字体、字号、颜色。
- 定义工厂：`GlyphFactory` 用 map 缓存，`GetGlyph` 命中返回缓存、未命中新建并缓存。
- 使用：渲染文本时，每个字符从工厂取享元，位置作为 `draw(x, y)` 的参数传入。

**是否使用：**

- 使用场景
  - 对象数量巨大，且对象内部有大量可共享的重复状态。
  - 内存压力大，对象创建与回收开销明显。
- 判断标准
  - 如果对象状态几乎各不相同，共享收益低，反而引入工厂复杂度，就不必用。

**Go 落地要点：**

- 享元对象必须不可变，否则一处修改会污染所有共享者。
- 工厂的缓存需要加锁保证并发安全；读多写少时可用 `sync.Map` 替代。
- 外在状态尽量是简单值（坐标、序号），作为方法参数传入，避免享元持有可变状态。
- 字符串驻留、数据库连接池、游戏地图里的地形/纹理复用都是享元思想的体现。

**相关模式：**

- 单例模式：单例是“只有一个实例”，享元是“共享多个实例”，工厂缓存可理解为多例。
- 组合模式：享元常与组合结合，共享叶子节点的通用状态。
