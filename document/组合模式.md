# 组合模式 Composite Design Pattern

**分类：** 结构型模式——把对象组织成树形结构，让客户端能以一致的方式处理单个对象（叶子）和组合对象（容器）。

## 定义

解决的问题：文件系统、组织架构这类天然带层级的数据，如果调用方每次都要区分"这是文件还是目录"来写不同的遍历、统计逻辑，代码里会到处是 `if` 类型判断，新增一种节点就要改所有调用点。

Go 中的落地：定义一个统一接口（`Node`），叶子（`File`）和容器（`Directory`）都实现它。容器内部持有子节点列表，操作时递归委托给子节点，调用方只面对 `Node`，不区分叶子与容器。

- 统一接口：`Node`，声明 `Name`、`Size`、`Print`
- 叶子：`File`，直接返回自身值
- 容器：`Directory`，`Size` 对所有子节点求和，`Print` 递归打印子树

## 实现方法

1. 抽出叶子与容器共同的能力，定义统一接口
2. 叶子直接实现接口，返回自己的数据
3. 容器实现接口并持有一个 `[]Node` 子节点切片，提供 `Add` 方法
4. 容器的接口方法遍历、递归子节点，把结果聚合返回

## 是否使用

- 数据可以抽象成"部分-整体"的树形层级结构
- 希望客户端统一处理单个对象和对象组合，消除类型分支
- 需要递归地统计、渲染、校验整棵树

判断标准：如果不存在天然的树形/层级关系，或者叶子与容器能力差异过大、硬塞进一个接口很别扭，就不要强行组合。

## Go 落地要点

- 叶子与容器实现同一接口是组合模式的核心，Go 隐式接口让这件事很轻
- 容器用 `[]Node` 存子节点，天然支持任意深度嵌套
- 聚合操作（如 `Size`）放在容器的递归实现里，叶子只返回自身值，职责清晰
- 别把 `Add` 放进统一接口——它只属于容器，否则叶子被迫实现无意义的方法；需要时可用类型断言单独处理

## 相关模式

- 责任链模式：组合树上的请求可以沿父→子方向传递，二者可配合
- 迭代器模式：可给组合结构写一个迭代器，屏蔽树形遍历细节
- 装饰器模式：装饰器也可以包装组合中的节点，动态增强行为
