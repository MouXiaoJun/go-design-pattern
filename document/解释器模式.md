# 解释器模式 Interpreter Design Pattern

**分类：** 行为型模式——为一种语言定义语法，并用解释器逐节点求值。

## 定义

**解决的问题：** 当需求里出现「一种可组合的小语言」——四则运算、规则表达式、查询条件、DSL——硬编码 `if/switch` 会随语法复杂度指数膨胀，而且语法一改就得改一堆地方。

**模式的做法：** 把语法翻译成一棵抽象语法树（AST），每种语法构造对应一个「表达式」节点，节点之间通过接口组合。求值就是递归遍历这棵树：终结符直接返回结果，非终结符先求子节点再按运算符计算。

**Go 中怎么落地：** 接口 + 组合。`Expression` 接口只有一个 `Interpret()` 方法，`Number` 是叶子节点，`Add/Sub/Mul/Div` 是内部节点、持有左右两个子表达式。解析器（Parser）负责把字符串切成 token，再按运算符优先级递归下降成 AST。

## 实现方法

1. 定义表达式接口 `Interpret() int`。
2. 实现终结符节点（数字）与非终结符节点（加减乘除）。
3. 写词法分析（tokenize）：把输入拆成数字和运算符。
4. 写递归下降解析：expr → term → factor，按优先级建树。
5. 求值 = 对根节点调用 `Interpret()`。

## 是否使用

**适用场景：**

- 语法稳定、规则不多的小语言（计算器、简单 DSL、规则引擎）。
- 需要把「表达逻辑」从代码里抽出来，让非程序员也能配置。

**判断标准：** 语法规则少且相对固定时，解释器模式清晰直观；一旦语法变复杂（函数、变量、类型、循环），手写解释器会失控，这时应换专用工具（parser 生成器、真正的语言或表达式引擎），而不是继续堆节点。

## Go 落地要点

- 接口要极简（一个 `Interpret` 方法就够），节点之间用组合而非继承。
- 递归下降解析比写一个大状态机更贴合 Go，也更容易读。
- 求值时注意除零、越界、非法 token 等错误，错误要显式返回而不是 `panic`。
- 这四个模式里解释器最「重」，Go 工程里更常见的是直接用现成表达式库；把它当理解语法树与编译原理的入门，价值大于当生产轮子。

## 相关模式

- 组合模式：AST 天然是一棵组合树。
- 访问者模式：当「求值」之外还想做类型检查、格式化、代码生成时，用访问者把操作从节点里抽出来。
